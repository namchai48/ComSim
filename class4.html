🃏 เกมจับคู่: KPI ↔ คำถามที่มันตอบได้

คลิกการ์ดซ้าย–ขวาให้จับคู่กันถูกต้อง

ครบทุกคู่!สังเกตว่า KPI แต่ละตัวตอบคำถามคนละคน — ผู้จัดการคลังสนใจ throughput/utilization · ฝ่ายการเงินสนใจค่าปรับ · หัวหน้ากะสนใจคิวค้าง · ข้อเสนอที่ดีต้องพูดกับทุกคนได้
กับดักที่ทำให้ข้อเสนอถูกตีตก รายงาน ค่าเฉลี่ยอย่างเดียว — "เวลาเฉลี่ย 38 นาที ต่ำกว่าเกณฑ์ 45 นาที ไม่ต้องทำอะไร" ฟังดูดี แต่ถ้าค่าสูงสุดคือ 145 นาที และมีรถค้างสิ้นกะ 8 คัน ระบบนี้กำลังมีปัญหาหนัก · ต้องรายงาน ค่าเฉลี่ย + ค่าสูงสุด + งานค้าง ควบคู่กันเสมอ

3 ทำไมต้องตรวจโมเดล — และ Verification ต่างจาก Validation อย่างไร

โมเดลที่มี bug จะยังรันได้และให้ตัวเลขหน้าตาน่าเชื่อถือ — นั่นคือสิ่งที่อันตรายที่สุด

💸 ราคาของโมเดลที่ผิด

  • โมเดลบอก "3 ช่องพอแล้ว" → ไม่ลงทุน → จ่ายค่าปรับปีละ 800,000 บาทต่อไปเรื่อย ๆ
  • โมเดลบอก "ต้องเปิดช่องที่ 4" → จ้างทีมเสริมเปิดตลอดกะ 2,400 บาท/วัน → เปิดจริงแล้วช่องว่างครึ่งวัน เพราะ bug ทำให้เวลาขนถ่ายยาวเกินจริง
  • ทั้งสองกรณี โค้ดรันผ่านทุกบรรทัด ไม่มี error สีแดงแม้แต่ตัวเดียว

💬 "All models are wrong, but some are useful" — George E. P. Box · เป้าหมายไม่ใช่โมเดลสมบูรณ์แบบ แต่คือ "ถูกต้องพอสำหรับการตัดสินใจนี้"

🔧 Verification (วันนี้)

"เราสร้างโมเดลถูกวิธีไหม?"
Did we build the model right?

  • เทียบ: โค้ด ↔ สิ่งที่เราออกแบบไว้
  • เครื่องมือ: output check, trace, ปิดความสุ่ม, extreme test, กฎของ Little, walkthrough
  • เปรียบ: ตรวจว่าก่อสร้างตรงตามแบบแปลน

🌍 Validation (ครั้งหน้า)

"เราสร้างโมเดลถูกตัวไหม?"
Did we build the right model?

  • เทียบ: โมเดล ↔ คลังจริง
  • เครื่องมือ: เทียบข้อมูลจริง, t-test, ถามหัวหน้ากะ, sensitivity
  • เปรียบ: ตรวจว่าแบบแปลนตรงกับความต้องการของผู้ใช้จริง
วิธีจำ Verification = ตรวจฝีมือช่าง (โค้ดตรงแบบไหม) · Validation = ตรวจกับดาต้าจริง (ตรงคลังจริงไหม) — ต้องทำควบคู่กันตลอด ไม่ใช่ทำครั้งเดียวตอนจบ

4 7 วิธี Verification — คลังเครื่องมือจับ bug

แต่ละวิธีเหมาะกับสถานการณ์ต่างกัน นักสร้างโมเดลที่ดีใช้หลายวิธีร่วมกัน

📖 คำศัพท์ใหม่ในหัวข้อนี้
  • ρ (rho) — อัตราส่วน "งานที่ต้องทำ ÷ กำลังการผลิตที่มี" บอกว่าระบบรับไหวหรือไม่ · ρ ≥ 1 = งานเข้าเร็วกว่าที่รับได้ คิวจะยาวขึ้นเรื่อย ๆ ไม่มีวันหยุด (อธิบายละเอียดในหัวข้อ 5)
  • assert — คำสั่งในโค้ดที่เช็คว่า "เงื่อนไขนี้ต้องเป็นจริงเสมอ" ถ้าเท็จเมื่อไรโปรแกรมจะหยุดทันทีตรงจุดนั้น เหมือนยามเฝ้าคอยดักค่าที่เป็นไปไม่ได้ทางตรรกะ (ตัวอย่างจริงในหัวข้อ 6–8)
  • trace — การ print เหตุการณ์ทุกอย่างพร้อมเวลาที่เกิดออกมาดูทีละบรรทัด เพื่อไล่เช็คว่าลำดับเหตุการณ์ตรงกับที่ตั้งใจออกแบบไว้ไหม
  • watch — ค่าที่เราคอยจับตาดูระหว่างรันโมเดล (เช่น ดูใน debugger หรือ log) คล้าย assert แต่แค่เตือน/แสดงผล ไม่หยุดโปรแกรม

🃏 เกมจับคู่: วิธีตรวจ ↔ ตัวอย่างการใช้จริงกับโมเดล dock

5 โมเดล dock — และเทคนิค "คาดผลก่อนรัน"

ถ้าไม่รู้ว่า "ควรได้เท่าไร" ก็ไม่มีทางรู้ว่าผลที่ได้ "ผิด" — ทำให้โมเดลง่ายจนคำนวณมือได้ก่อน

📐 2 กติกาที่ทำให้ 7 วิธีได้ผลจริง

เครื่องมือทั้ง 7 วิธีอยู่ในหัวข้อ 4 แล้ว — สองข้อนี้ไม่ใช่วิธีใหม่ แต่คือเงื่อนไขการใช้ที่ทำให้เครื่องมือพวกนั้นจับ bug ได้จริง

  1. คาดผลก่อนรันเสมอ — เขียนค่าที่ควรได้ลงกระดาษก่อนกดปุ่ม (คำนวณกำลังผลิตเทียบปริมาณงาน หรือคิด ρ) · ถ้าดูผลก่อนแล้วค่อยคิด สมองจะหาเหตุผลเข้าข้างตัวเลขที่เห็นเสมอ — ทุกวิธีในหัวข้อ 4 ใช้ไม่ได้เลยถ้าไม่มี "ค่าที่คาดไว้" มาเทียบ
  2. ตรวจระหว่างสร้าง ไม่ใช่ตอนจบ — เพิ่มโค้ดทีละส่วน ตรวจทีละส่วน · bug ที่เจอตอนเขียน 20 บรรทัดแรกใช้เวลาแก้ 2 นาที · bug เดียวกันที่เจอตอนโมเดลเสร็จแล้ว 150 บรรทัดใช้เวลาทั้งบ่าย

✏️ คำนวณมือก่อน — "ช่วงบ่ายรถล้นจริงไหม"

ช่วงรถเข้างานที่ต้องทำกำลังผลิต (3 ช่อง)ρ = งาน ÷ กำลัง
เช้า (0–240 น.)เฉลี่ยทุก 10 นาที ≈ 24 คัน24 × 22 = 528 นาที3 × 240 = 720 นาที0.73 — สบาย
บ่าย (240–480 น.)เฉลี่ยทุก 6 นาที ≈ 40 คัน40 × 22 = 880 นาที3 × 240 = 720 นาที1.22 — รับไม่ไหว!
อ่านค่า ρ (rho) ให้เป็น ρ = ปริมาณงาน ÷ กำลังการผลิต · ρ ≥ 1 = คิวโตขึ้นเรื่อย ๆ ไม่มีวันหยุด · ρ ≈ 0.85–0.95 = คิวยาวแต่ยังไม่ระเบิด · ρ < 0.7 = สบาย
→ หัวหน้ากะพูดถูก และเรารู้ตั้งแต่ยังไม่รันโมเดลว่า "ปัญหาอยู่ช่วงบ่าย" · ถ้าโมเดลรันออกมาแล้วบอกว่าช่วงบ่ายสบาย = มี bug แน่นอน

🐍 โค้ดโมเดล dock (ฉบับถูกต้อง — คัดลอกไปใช้ใน Colab ได้เลย)

จุดที่ยากที่สุดคือ ทางเลือก C: ช่องที่ 4 เปิดกลางกะ — SimPy เพิ่ม capacity ตรง ๆ ไม่ได้ เราจึงใช้ทริก "จองช่องไว้ก่อน แล้วค่อยปล่อยคืนตอนทีมเสริมมา"

# ===== คิวรถบรรทุกที่ประตูขนถ่าย (dock) =====
import simpy, random

SHIFT      = 480    # กะละ 8 ชั่วโมง
NOON       = 240    # เส้นแบ่งเช้า/บ่าย
IAT_AM     = 10     # เช้า: รถเข้าเฉลี่ยทุก 10 นาที
IAT_PM     = 6      # บ่าย: รถเข้าเฉลี่ยทุก 6 นาที (พีค)
SVC        = (12, 20, 34)   # เวลาขนถ่าย Triangular(ต่ำสุด, ฐานนิยม, สูงสุด) เฉลี่ย 22
BASE_DOCKS = 3
EXTRA_FROM = 240    # ทีมเสริมเปิดช่องที่ 4 ตั้งแต่นาทีนี้ (None = ไม่มีทีมเสริม)

log = []          # เก็บทุกคัน: (มาถึง, เริ่มขนถ่าย, ออก)
busy = 0.0
n_arrived = 0     # นับรถที่เข้าระบบทั้งหมด (ใช้ตรวจในหัวข้อ 8)

def truck(env, name, dock):
    global busy
    arrive = env.now
    with dock.request() as req:
        yield req
        start = env.now
        s = random.triangular(*SVC)
        busy += s
        yield env.timeout(s)
    log.append((arrive, start, env.now))     # รอ = start - arrive

def arrivals(env, dock):
    global n_arrived
    while True:
        mean = IAT_AM if env.now < NOON else IAT_PM   # อัตราต่างกันตามช่วงเวลา
        yield env.timeout(random.expovariate(1/mean))
        if env.now >= SHIFT: break                    # หมดกะ ไม่รับรถใหม่
        n_arrived += 1
        env.process(truck(env, n_arrived, dock))

def extra_team(env, dock):
    # ★ ทริก: จองช่องที่ 4 ไว้ตั้งแต่ต้นกะ แล้วปล่อยคืนตอนทีมเสริมมาถึง
    req = dock.request()
    yield req
    yield env.timeout(EXTRA_FROM)
    dock.release(req)
    print(f"t={env.now:6.1f}  ทีมเสริมมาถึง เปิดช่องที่ 4")

random.seed(42)
env  = simpy.Environment()
n_docks = BASE_DOCKS + (1 if EXTRA_FROM is not None else 0)
dock = simpy.Resource(env, capacity=n_docks)
env.process(arrivals(env, dock))
if EXTRA_FROM is not None: env.process(extra_team(env, dock))
env.run(until=SHIFT)

# dock-minutes ที่มีจริง = 3 ช่องเต็มกะ + ช่องที่ 4 เฉพาะช่วงที่เปิด
dock_min = BASE_DOCKS*SHIFT + (SHIFT - EXTRA_FROM if EXTRA_FROM is not None else 0)
print(f"Utilization = {busy/dock_min:.1%}")
3 จุดที่พลาดกันบ่อยที่สุด ① turnaround ≠ waiting — turnaround = ออก − มาถึง (รวมเวลาขนถ่าย) · waiting = เริ่มขนถ่าย − มาถึง · ② ตัวหาร utilization ต้องเป็น dock-minutes ที่มีจริง ไม่ใช่ 480 · ③ รถที่ค้างตอนหมดกะ จะไม่ถูก log.append เลย ต้องนับแยกต่างหาก

# ===== ขั้นที่ 3 — วางเป็น "เซลล์ใหม่" ต่อท้าย (คิด Lq ย้อนหลังจาก log ได้เลย) =====
ev = sorted([(a, +1) for a,s,d in log] + [(s, -1) for a,s,d in log])
area = 0.0; q = 0; last = 0.0
for t, d in ev:
    area += q * (t - last); last = t; q += d
area += q * (SHIFT - last)

Lq = area / SHIFT
lam = len(log) / SHIFT
Wq = sum(wait) / len(wait)
print(f"Lq (พื้นที่ใต้กราฟ) = {Lq:.2f} คัน")
print(f"λ × Wq            = {lam*Wq:.2f} คัน   → ต่างกัน {abs(Lq - lam*Wq):.3f}")
