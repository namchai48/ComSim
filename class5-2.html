1 เชื่อมจากครั้งที่แล้ว — จาก "ไม่มี bug" สู่ "ตรงกับความจริง"

ครั้งที่ 4 เราตรวจโค้ด · วันนี้เราตรวจสมมติฐาน ซึ่งอันตรายกว่ามาก เพราะมันไม่มีทางโผล่เป็น error

  • โมเดล dock ที่ผ่าน Verification แล้ว — สมดุลเข้า–ออก · trace · assert · extreme test · กฎของ Little

Verification ถามว่า "โค้ดตรงแบบไหม" · Validation ถามว่า "แบบตรงกับความจริงไหม" · Credibility ถามว่า "คนที่ต้องใช้เชื่อไหม"

🧩 3 ประเภทของ Validity ที่ต้องตรวจให้ครบ

ประเภทตรวจอะไรตัวอย่างในเคส dock
① Conceptual validity
แนวคิด/ขอบเขต		 โครงสร้างโมเดลสะท้อนระบบจริงไหม · สิ่งที่ตัดทิ้งสำคัญหรือเปล่า โมเดลสมมติรถทุกคันเหมือนกันหมด — คลังจริงมีรถพ่วงที่ขนถ่ายนานกว่าไหม? มีรถด่วนที่ได้คิวก่อนไหม?
② Data validity
ข้อมูลนำเข้า		 ตัวเลขและการแจกแจงที่ใส่เข้าไป มาจากข้อมูลจริงหรือเดาเอา Triangular(12, 20, 34) มาจากจับเวลาจริงกี่คัน? ระยะห่างรถเข้า 10/6 นาที มาจาก log ประตูกี่วัน?
③ Operational validity
ผลลัพธ์		 ผลที่โมเดลให้ ใกล้เคียงกับที่ระบบจริงทำได้ไหม turnaround เฉลี่ยที่โมเดลทำนาย ตรงกับ log ประตูคลังจริงไหม (ทดสอบด้วย t-test)
ลำดับที่ถูกต้อง ตรวจ ① ก่อนเสมอ — ถ้าแนวคิดผิด การไปปรับตัวเลข (②) หรือเทียบผล (③) ก็ไม่ช่วยอะไร · โมเดลที่ลืมว่าคลังจริงหยุดพักเที่ยง ต่อให้ป้อนเวลาขนถ่ายแม่นแค่ไหนก็ยังตอบผิด

3 โมเดลที่จะเอามา Validate — อ่านโค้ดใหม่ในฐานะ "รายการสมมติฐาน"

โมเดลตัวเดียวกับครั้งที่ 4 · ครั้งนั้นเราอ่านมันเพื่อหา bug — วันนี้อ่านเพื่อหาว่ามันสมมติอะไรกับคลังจริงไว้บ้าง

📎 ใช้โมเดลของกลุ่มตัวเอง เปิด Colab ของกลุ่มที่ผ่าน Verification จากครั้งที่ 4 ขึ้นมา — ห้ามเขียนใหม่ เพราะสิ่งที่เราจะตรวจวันนี้คือโมเดลตัวที่จะเอาไปเสนอจริง
ถ้ากลุ่มไหนโค้ดหาย ใช้เวอร์ชันมาตรฐานด้านล่างแทนได้

🐍 โมเดล dock (เวอร์ชันมาตรฐาน — ตั้งค่าสถานการณ์เริ่มต้น 3 ช่อง)

# ===== คิวรถบรรทุกที่ประตูขนถ่าย (dock) =====
import simpy, random

SHIFT      = 480    # กะละ 8 ชั่วโมง
NOON       = 240    # เส้นแบ่งเช้า/บ่าย
IAT_AM     = 10     # เช้า: รถเข้าเฉลี่ยทุก 10 นาที
IAT_PM     = 6      # บ่าย: รถเข้าเฉลี่ยทุก 6 นาที (พีค)
SVC        = (12, 20, 34)   # เวลาขนถ่าย Triangular(ต่ำสุด, ฐานนิยม, สูงสุด) เฉลี่ย 22
BASE_DOCKS = 3
EXTRA_FROM = None   # สถานการณ์เริ่มต้น: ไม่มีทีมเสริม

log = []          # เก็บทุกคัน: (มาถึง, เริ่มขนถ่าย, ออก)
busy = 0.0; n_arrived = 0

def truck(env, name, dock):
    global busy
    arrive = env.now
    with dock.request() as req:
        yield req
        start = env.now
        s = random.triangular(SVC[0], SVC[2], SVC[1])   # Python รับ (ต่ำสุด, สูงสุด, ฐานนิยม)
        busy += s
        yield env.timeout(s)
    log.append((arrive, start, env.now))     # รอ = start - arrive

def arrivals(env, dock):
    global n_arrived
    while True:
        mean = IAT_AM if env.now < NOON else IAT_PM
        yield env.timeout(random.expovariate(1/mean))
        if env.now >= SHIFT: break
        n_arrived += 1
        env.process(truck(env, n_arrived, dock))

random.seed(42)
env  = simpy.Environment()
dock = simpy.Resource(env, capacity=BASE_DOCKS)
env.process(arrivals(env, dock))
env.run(until=SHIFT)

ta = [e - a for a, st, e in log]          # turnaround รายคัน (นาที)
print(f"รถเข้า {n_arrived} · เสร็จ {len(log)} · turnaround เฉลี่ย {sum(ta)/len(ta):.1f} นาที")
⚠️ จุดที่เพิ่งแก้ — ลำดับอาร์กิวเมนต์ของ random.triangular Python รับ triangular(ต่ำสุด, สูงสุด, ฐานนิยม) ไม่ใช่ (ต่ำสุด, ฐานนิยม, สูงสุด) · ถ้าเขียน random.triangular(*SVC) ตรง ๆ โมเดลจะสุ่มเวลาขนถ่ายอยู่ในช่วง 12–25.3 นาที เฉลี่ย 20.8 แทนที่จะเป็น 12–34 เฉลี่ย 22 ตามที่ตั้งใจ
👉 เป็น bug ที่ไม่มี error ฟ้อง ผลลัพธ์ยังดูสมเหตุสมผล จึงรอดจาก verification มาได้ — ตัวอย่างชั้นดีว่าทำไม "โค้ดรันผ่าน" ไม่เท่ากับ "โค้ดถูก"

🔍 โค้ดบรรทัดไหน = สมมติฐานอะไร

นี่คือหัวใจของ conceptual validity — สมมติฐานไม่ได้อยู่ในเอกสาร มันอยู่ในโค้ดที่เราเขียนเอง และหลายข้อเราใส่ไปโดยไม่รู้ตัว

บรรทัดในโค้ดแปลว่าเราสมมติว่า...
random.triangular(…)รถทุกคันเหมือนกันหมด — ไม่มีรถพ่วงที่ขนถ่ายนานกว่า ไม่มีของที่ต้องตรวจนับพิเศษ
dock.request() ธรรมดาเข้าคิวมาก่อนได้ก่อน — ไม่มีรถด่วน ไม่มีการจัดคิวใหม่ตามชนิดสินค้า
capacity=BASE_DOCKSทั้ง 3 ช่องทำงานเท่ากันและว่างตลอดกะ — ไม่มีช่องเสีย ไม่มีคนพักเที่ยง
random.expovariate(1/mean)รถมาแบบสุ่มอิสระต่อกัน — ไม่มีการนัดเวลาล่วงหน้า ไม่มีรถมาเป็นขบวนพร้อมกัน
IAT_AM ... else IAT_PMอัตรารถเข้าเปลี่ยนที่นาทีที่ 240 พอดี — ของจริงพีคอาจเริ่มเร็ว/ช้ากว่านั้น หรือค่อย ๆ ไต่
if env.now >= SHIFT: breakรถที่มาไม่ทันกะหายไปเฉย ๆ — ของจริงไปต่อคิวกะถัดไป หรือทำ OT
ไม่มีในโค้ดเลยไม่มีเวลาเอกสาร/ตรวจของ · ไม่มีรถเสีย · ไม่มีฝนตก · รถไม่เคยมาแล้วไม่มีของให้ขน
แถวสุดท้ายอันตรายที่สุด สมมติฐานที่ไม่ปรากฏในโค้ดคือสิ่งที่หาไม่เจอด้วยการอ่านโค้ด — เจอได้ทางเดียวคือไปดูของจริงหรือถามคนหน้างาน ซึ่งเป็นเรื่องของหัวข้อ 4–5

4 วิธีการทำ Validity — เครื่องมือที่ใช้ควบคู่กับทั้ง 3 ประเภท

หัวข้อ 2 บอกว่า "ตรวจอะไร" · หัวข้อนี้บอกว่า "ตรวจด้วยอะไร" — สองอย่างนี้อยู่คนละมิติ ไม่ใช่ขั้นตอนที่ทำต่อกัน

🛠️ 4 วิธีที่ใช้ในคาบนี้ — วิธีไหนยืนยันประเภทไหน

วิธีตรวจยืนยันประเภทจับอะไรได้ที่วิธีอื่นจับไม่ได้ต้นทุน
① Face validity
ถามคนที่ทำงานจริง (หัวข้อ 5)		 ①②③ สมมติฐานที่หลุด · กิจกรรมที่โมเดลลืมใส่ทั้งกิจกรรม — เป็นวิธีเดียวที่จับปัญหาเชิงแนวคิดได้ ถูกและเร็วที่สุด
② ตามรอยที่มาข้อมูล + histogram
(หัวข้อ 6)		 ② ใช้ค่าเฉลี่ยแทนการแจกแจง · ข้อมูลล้าสมัย ปัดเศษ หรือหายไปอย่างมีระบบ กลาง — ต้องขอ log จริง
③ t-test เทียบข้อมูลจริง
(หัวข้อ 7)		 ③ ผลโมเดลเบี่ยงจากของจริงอย่างมีนัยสำคัญ พร้อมบอกขนาดความต่างด้วยช่วงความเชื่อมั่น แพงที่สุด — ต้องเก็บข้อมูลจริง
④ Sensitivity analysis
(หัวข้อ 8)		 ① และข้อจำกัด ข้อสรุปที่เปราะ — พึ่งสมมติฐานที่เรายังไม่มั่นใจ · บอกว่าควรไปเก็บข้อมูลอะไรเพิ่ม ถูก แต่ต้องมีโมเดลก่อน
ทำ 1 ครั้ง ติ๊กได้หลายช่อง พาหัวหน้าคลังมาดูกราฟหนึ่งรอบ = ได้หลักฐานทั้ง ① Conceptual (เขาทักว่าสมมติฐานไหนไม่จริง) และ ③ Operational (เขาบอกว่าตัวเลขเหมือน/ไม่เหมือนของจริง) พร้อมกัน — นี่คือความหมายของคำว่า "ควบคู่"

ช่องขนถ่ายทำงานต่อเนื่องตลอด 480 นาที⚠️ สูงถ้าคลังจริงพักเที่ยงพร้อมกัน 30–45 นาที กำลังผลิตหายไปทั้งก้อนในช่วงที่รถเริ่มแน่นพอดี → คิวสะสมที่โมเดลมองไม่เห็น · ทดลองแล้ว: พักพร้อมกัน 30 นาที ค่าปรับเพิ่มเท่าตัว (~40,000 → ~80,000 บาท/กะ)

รถมาแบบสุ่มอิสระ (Exponential)⚠️ สูงถ้ามีการนัดเวลาหรือรถมาเป็นขบวน คิวจะกระจุกกว่าที่โมเดลคิดมาก — ทดลองแล้ว: มาเป็นขบวนละ 2 คัน ค่าปรับ +61% · ขบวนละ 3 คัน +87% คือแรงพอ ๆ กับการพักเที่ยง · ต้องดู log จริงว่ารถมาแบบไหน
พีคเริ่มที่นาทีที่ 240 พอดีกลางไม่ได้กระทบทุกทางเลือกเท่ากัน — A กับ B ไม่ผูกกับเวลา แต่ ทางเลือก C ผูกกับนาทีที่ 240 ตรง ๆ · ทดลองแล้ว: ถ้าพีคจริงเริ่มนาที 240–280 ต้นทุนรวมของ B กับ C แยกไม่ออก แต่ถ้าพีคจริงเริ่มเร็วกว่านั้น (นาที 200) B ถูกกว่า C อย่างชัดเจน → สมมติฐานนี้เปลี่ยนคำตอบได้
ทั้ง 3 ช่องเหมือนกันหมดต่ำถ้าไม่มีช่องไหนใช้กับรถบางประเภทไม่ได้ ก็ยอมรับได้ในโมเดลรุ่นแรก
ไม่มีเวลาเอกสาร/ตรวจนับแยกต่างหากต่ำถ้ารวมอยู่ในเวลาขนถ่ายที่จับมาแล้วก็ไม่ต้องแยก — แต่ต้องยืนยันว่าคนจับเวลารวมให้จริง
📐 ทำไม "ความแปรปรวน" ถึงสำคัญน้อยกว่าที่คิดในโมเดลตัวนี้ — ดูที่โหลดของช่วงบ่าย ช่วงบ่ายมีรถเข้า ~40 คัน × 22 นาที = 880 dock-นาทีที่ต้องทำ แต่มีกำลังผลิตแค่ 3 ช่อง × 240 นาที = 720 dock-นาที → โหลด 122%
ระบบที่โหลดเกิน 100% คิวจะสะสมขึ้นเรื่อย ๆ ตามกำลังผลิตที่ขาด ไม่ได้ขึ้นกับความแปรปรวนเป็นหลัก · สมมติฐานที่ขยับค่าเฉลี่ยเวลาขนถ่ายหรือกำลังผลิตที่หายไป จึงอันตรายที่สุด
👉 กลับกัน ถ้าเปิดช่องที่ 4 จนระบบไม่ล้นแล้ว ลำดับความอันตรายจะเปลี่ยน — ความแปรปรวนจะกลับมามีน้ำหนักมากขึ้น · "อันตราย" จึงไม่ใช่คุณสมบัติของสมมติฐานอย่างเดียว แต่ขึ้นกับจุดทำงานของระบบด้วย
จุดสังเกต — แยกให้ออกว่าอันไหน "เข้าใจระบบผิด" อันไหน "สรุปผลผิด" ข้อ 1 · 2 · 4 เป็น Conceptual validity — คือโมเดลเข้าใจระบบผิด ไม่ใช่ตัวเลขผิด · ปัญหาแบบนี้แก้ด้วยการจูนพารามิเตอร์ไม่ได้เลย ต้องแก้โครงสร้างโมเดล · และวิธีเดียวที่จะเจอคือไปคุยกับคนหน้างาน
ส่วนข้อ "รถค้างหายจากระบบ" ไม่ใช่ conceptual validity — เป็นการตัดข้อมูลทิ้งตอนสรุปผล (censoring) ซึ่งแก้ได้ที่โค้ดล้วน ๆ คือรันต่อจนรถหมดคิวแล้วนับรถค้างแยกออกมา ไม่ต้องแก้ความเข้าใจระบบเลย

7 Operational Validity — ทดสอบด้วย t-test

คำถาม: "turnaround ที่โมเดลทำนาย ต่างจาก log ประตูคลังจริงอย่างมีนัยสำคัญไหม" — ครั้งนี้เราอยากให้ไม่ต่าง

❓ t-test คืออะไร สำคัญยังไง t-test คือการทดสอบทางสถิติที่บอกว่าค่าเฉลี่ยของสองกลุ่มต่างกันจริง หรือต่างกันเพราะความบังเอิญจากการสุ่มตัวอย่าง · สำคัญเพราะเป็นเครื่องมือหลักที่ใช้เทียบผลจากโมเดลกับข้อมูลจริง เพื่อบอกว่าโมเดลที่สร้างขึ้นเชื่อถือได้แค่ไหน

🔬 ตรรกะที่กลับหัวจากที่เคยเรียน

สมมติฐาน

  • H₀ : μโมเดล = μจริง (ไม่ต่างกัน)
  • H₁ : μโมเดล ≠ μจริง (ต่างกัน)

การตีความ

  • p > 0.05 → ปฏิเสธ H₀ ไม่ได้ → โมเดลผ่าน ✅
  • p ≤ 0.05 → ต่างกันอย่างมีนัยสำคัญ → ต้องแก้โมเดล ⚠️
อย่าเข้าใจผิด "p > 0.05" ไม่ได้แปลว่าโมเดลถูก — แปลว่า "ข้อมูลที่มียังไม่พอจะบอกว่าต่างกัน" · ถ้าข้อมูลจริงมีแค่ 5 ค่า แทบไม่มีทางเจอความต่างเลยไม่ว่าโมเดลจะแย่แค่ไหน · ข้อมูลน้อย = การทดสอบอ่อน ไม่ใช่โมเดลดี
❓ CI (ช่วงความเชื่อมั่น) คืออะไร หมายความว่ายังไง CI ย่อจาก confidence interval คือช่วงตัวเลขที่ "ผลต่างจริง" ระหว่างโมเดลกับของจริง น่าจะอยู่ตรงนั้น เช่น CI = [−1.3, +9.3] นาที แปลว่าของจริงอาจต่างจากโมเดลได้ตั้งแต่ −1.3 ถึง +9.3 นาที · ถ้าช่วงนี้คร่อมเลข 0 ก็แปลว่าผลต่างเป็นศูนย์ยังเป็นไปได้ ซึ่งตรงกับ p > 0.05 เสมอ · CI มีประโยชน์เพราะบอกขนาดเป็นนาทีที่เอาไปเทียบกับเกณฑ์งานจริงได้ตรง ๆ ซึ่ง p อย่างเดียวทำไม่ได้

📊 วิธีที่ 1 — ทำ t-test ใน Excel

' ข้อมูล: A2:A121 = turnaround จาก log จริง 120 คัน · B2:B1001 = ผลโมเดล
' ตั้งชื่อเซลล์ไว้ก่อน: vA,vB = VAR.S ของแต่ละกลุ่ม · nA,nB = COUNT ของแต่ละกลุ่ม

p-value  =T.TEST(A2:A121, B2:B1001, 2, 3)          ' 2 = สองหาง · 3 = Welch
ผลต่าง    =AVERAGE(A2:A121) - AVERAGE(B2:B1001)
SE       =SQRT(vA/nA + vB/nB)
df       =(vA/nA+vB/nB)^2 / ((vA/nA)^2/(nA-1) + (vB/nB)^2/(nB-1))
CI ล่าง   =ผลต่าง - T.INV.2T(0.05, df) * SE
CI บน     =ผลต่าง + T.INV.2T(0.05, df) * SE
ทางลัด Data → Data Analysis → t-Test: Two-Sample Assuming Unequal Variances ให้ t · df · p ในตารางเดียว ไม่ต้องพิมพ์สูตร — แต่ไม่ให้ช่วงความเชื่อมั่น จึงยังต้องคำนวณ 3 บรรทัดล่างเอง

🐍 วิธีที่ 2 — ทำ t-test ใน Python

ให้ผลตรงกับสูตร Excel ข้างบนทุกตัวเลข · equal_var=False คือตัวเดียวกับอาร์กิวเมนต์ 3 ใน T.TEST

from scipy import stats

res = stats.ttest_ind(real_time, model_time, equal_var=False)   # Welch = T.TEST(...,2,3)
ci  = res.confidence_interval(0.95)

print(f"t = {res.statistic:.3f} · p = {res.pvalue:.4f}")
print(f"CI 95% ของผลต่าง = [{ci.low:.2f}, {ci.high:.2f}]")
print("✅ ยังไม่พบว่าต่างกัน" if res.pvalue > 0.05 else "⚠️ ต่างอย่างมีนัยสำคัญ ต้องแก้โมเดล")
อย่าอ่านแค่ p บรรทัด ci มีไว้โดยตั้งใจ — เพราะ p = 0.31 ที่มาจากข้อมูล 5 ใบ กับ p = 0.31 ที่มาจากข้อมูล 500 ใบ มีน้ำหนักต่างกันคนละเรื่อง แต่ตัว p เองไม่บอกเรา · ช่วงความเชื่อมั่นบอก

# ===== 3.3 t-test 2 ชุด: "ช่วงเช้า" และ "ทั้งกะ" =====
from scipy import stats

def compare(mask_real, mask_model, ชื่อ):
    real  = log_real[mask_real].groupby("วันที่")["ta"].mean().values
    model = [d[mask_model(d)]["ta"].mean() for d in model_days]
    r = stats.ttest_ind(real, model, equal_var=False)
    print(f"{ชื่อ}: จริง {np.mean(real):.1f} · โมเดล {np.mean(model):.1f} · ต่าง {np.mean(real)-np.mean(model):+.1f} นาที · p = {r.pvalue:.3f}")

compare(log_real["นาทีที่เข้า"] < 240, lambda d: d["arrive"] < 240, "เฉพาะรถที่เข้าก่อน 12:00")
compare(log_real["นาทีที่เข้า"] >= 0,  lambda d: d["arrive"] >= 0,  "ทั้งกะ")

🔍 4 คำถามที่ต้องตอบตัวเองให้ได้ ก่อนกรอกเช็กลิสต์

ตอบเป็นข้อ ๆ ในกลุ่ม — ข้อไหนตอบไม่ได้ ห้ามติ๊กเช็กลิสต์ข้อนั้น

คำถามตอบให้ได้ว่า
① เจออะไรบ้าง คลัง A ต่างจากโมเดลตรงไหน — และหลักฐานชิ้นไหนที่ทำให้พูดแบบนั้นได้ (histogram? กราฟรถเข้าต่อชั่วโมง? p-value? ประโยคในบทสัมภาษณ์?)
② ตกอะไรไปหรือเปล่า ถ้าตรวจแล้วไม่เจออะไรเลย ให้กลับไปดูว่ายังไม่ได้ตรวจอะไรบ้าง — เช่น ยังไม่ได้ดูรูปร่างการแจกแจง ยังไม่ได้ดูจำนวนรถต่อวัน ยังไม่ได้เช็กว่าข้อมูลครบไหม
③ ถ้าหัวหน้าคลังมานั่งตรงนี้ เขาจะถามอะไร ตั้งคำถามใส่ตัวเองอย่างน้อย 3 ข้อ จากคำถาม 5 ข้อในหัวข้อ 5 แล้วตอบให้ครบ · ตอบว่า "เดาเอา" ได้ ถ้าบันทึกไว้อย่างซื่อสัตย์ในตารางข้อมูลนำเข้า (หัวข้อ 9 ขั้นที่ 2)
④ แก้แล้วข้อสรุปทนไหม ถ้าสมมติฐานที่เรายังไม่มั่นใจที่สุดผิด — ข้อสรุปเรื่อง "ควรเพิ่มช่องที่ 4 ไหม" ยังเหมือนเดิมหรือพลิก (ใช้ผล sensitivity จากหัวข้อ 8)
กับดักของการตรวจงานตัวเอง คนเราหาข้อผิดของตัวเองไม่เจอ เพราะเราตรวจในสิ่งที่เราคิดว่าถูกอยู่แล้ว — วิธีแก้คือให้สมาชิกคนหนึ่งในกลุ่มรับบทคนที่ต้องคัดค้านโมเดลนี้ให้ได้ แล้วบังคับตัวเองว่าต้องหาจุดอ่อนให้ได้อย่างน้อย 2 ข้อ ก่อนจะสรุปว่าโมเดลผ่าน

✅ เช็กลิสต์ Validation 0/7

เช็กลิสต์แยกเป็น 2 ก้อน เพราะเป็นคนละคำถาม — ก้อนแรกถามว่า "ตรวจครบทุกด้านหรือยัง" · ก้อนที่สองถามว่า "ใช้วิธีอะไรเป็นหลักฐาน"
ติ๊กเฉพาะข้อที่ ทำจริงและมีหลักฐาน — ไม่ใช่ข้อที่ "น่าจะโอเค"

🎯 ก้อนที่ 1 · ตรวจครบทุกด้านหรือยัง 0/3
  • ① Conceptual validity — เขียนสมมติฐานหลักครบทุกข้อ และรู้ว่าข้อไหนผิดแล้วข้อสรุปพลิก
  • ② Data validity — ทุกตัวเลขนำเข้าบอกที่มาได้ และรู้ว่ามั่นใจกับแต่ละตัวแค่ไหน
  • ③ Operational validity — ผลที่โมเดลให้ ใกล้เคียงกับที่ระบบจริงทำได้ (หรือระบุชัดว่ายังไม่มีข้อมูลมาเทียบ)
🛠️ ก้อนที่ 2 · ใช้วิธีอะไรเป็นหลักฐาน 0/4
  • Face validity — เอาสมมติฐานทุกข้อไปเทียบกับบทสัมภาษณ์หัวหน้าคลัง (และให้อาจารย์ดูผลที่เป็นรูปธรรม) แล้วไม่มีข้อไหนขัดกับที่เขาเล่า → ยืนยัน ① และ ③
  • ตามรอยที่มาข้อมูล + histogram — เปิด log จริง ดูรูปร่างการแจกแจง ไม่ใช้ค่าเฉลี่ยแทนการแจกแจง → ยืนยัน ②
  • t-test เทียบข้อมูลจริง — เทียบค่าเฉลี่ยรายวันของโมเดล 20 รอบ กับ log ประตูจริง 20 วัน ทั้งช่วงเช้าและทั้งกะ → ยืนยัน ③
  • Sensitivity analysis — เปลี่ยนสมมติฐานสำคัญแล้วดูว่าข้อสรุปพลิกไหม อย่างน้อย 2 ตัวแปร → ยืนยัน ①
ครบ 7 ข้อ! 🏆กระบวนการ Validation ครบถ้วนแล้ว — ตรวจครบทุกด้าน มีหลักฐานทุกวิธี และรู้ชัดว่าโมเดลยังไม่ผ่านตรงไหน · ครั้งหน้า (ครั้งที่ 6) เราจะแก้โมเดลตามหลักฐานที่เจอวันนี้ รันซ้ำหลายรอบ สร้างช่วงความเชื่อมั่น แล้วตัดสินใจเรื่องช่องที่ 4 อย่างมีหลักฐาน

📝 สรุปผลการตรวจของกลุ่ม

ช่องนี้คือผลจากการตรวจงานตัวเองข้างบน — เขียนตามที่ตรวจเจอจริง ๆ · ระบบบันทึกอัตโนมัติในเบราว์เซอร์เครื่องนี้

เขียนข้อจำกัดเองก่อนที่คนอื่นจะจับได้ กลุ่มที่บอกเองว่า "ตรงนี้เรายังไม่ได้ตรวจ" ดูน่าเชื่อถือกว่ากลุ่มที่บอกว่าทุกอย่างเรียบร้อย — เพราะไม่มีโมเดลไหนเรียบร้อยจริง

📤 ส่งออกรายงานผล Validation

ระบบจะรวมทุกอย่างที่กรอกไว้ในหัวข้อ 9 และ 10 — สมมติฐาน · ตารางข้อมูลนำเข้า · ตัวเลขผลลัพธ์ · เช็กลิสต์ 9 ข้อ · จุดที่ยังไม่ผ่าน — เป็นไฟล์เดียวสำหรับส่งอาจารย์

📚 สรุปคาบนี้

  • Verification = โค้ดตรงแบบไหม · Validation = แบบตรงความจริงไหม · Credibility = คนใช้เชื่อไหม
  • 3 validity: Conceptual (แนวคิด) → Data (ข้อมูลนำเข้า) → Operational (ผลลัพธ์) · ต้องตรวจตามลำดับนี้
  • Face validity คือเครื่องมือที่ถูกและเร็วที่สุด — เอาผลที่เป็นรูปธรรมไปให้คนหน้างานดู
  • t-test: p > 0.05 = ยังไม่พบความต่าง (ไม่ใช่ "โมเดลถูก") · ข้อมูลน้อย = การทดสอบอ่อน
  • Sensitivity: ถ้าเปลี่ยนสมมติฐานแล้วข้อสรุปพลิก แสดงว่าต้องเก็บข้อมูลเพิ่มก่อนตัดสินใจ
  • ทักษะ Excel ที่ได้: T.TEST · VAR.S/COUNT · T.INV.2T สำหรับช่วงความเชื่อมั่น · Data Analysis ToolPak
  • ครั้งหน้า (ครั้งที่ 6 — ครั้งสุดท้าย): แก้โมเดลตามหลักฐานจากคาบนี้ (แยกรถ 2 ประเภท) · รันซ้ำหลายรอบ · ช่วงความเชื่อมั่น · เปรียบเทียบทางเลือกอย่างมีหลักฐาน · เขียน decision memo เสนอผู้บริหาร
